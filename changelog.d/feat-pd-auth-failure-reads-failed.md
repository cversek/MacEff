### Added

- **A session that can't authenticate reads failed** (MIS-0002-R19). The session's transcript monitor reads Claude Code's failed-login entry (an assistant API error with `error: "authentication_failed"`, such as "Login expired" or the API's 401) as the line arrives, and its beat carries what the client said in the new `pd_unit_alive` field `auth_failed` until a reply shows a request went through. The core reads the session failed with that reason, and doesn't stop or restart it: a restart can't log in, and a restarted session nobody prompts would read healthy again while it still can't. When a reply comes through, the same process reads running. A daemon that starts meanwhile adopts the session rather than starting a second one. If the beat stops too, the session fails and restarts as before. An assistant entry the client writes itself (model `<synthetic>`, such as "No response requested.") neither fails nor restores the login, since no request was made. The monitor logs `auth_failure_detected` and `auth_recovered` once each. Eight planted defects each failed a test, among them the core's half removed and the synthetic entry read as a reply.
