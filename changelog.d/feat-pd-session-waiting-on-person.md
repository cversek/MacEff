### Added

- **The session unit reports a permission dialog as waiting on a person** (`permission_watch.SessionDialogs`, `pd/liveness.py`, `transcript_monitor/daemon.py`, policy `persistent_layer` 6.2; MIS-0002-R21). The session's transcript monitor already beats for the unit. Each beat now carries `waiting_on` when the event log shows that session's newest deciding event is a permission request, by the rule `permissions pending` uses, so the core moves the unit to waiting on a person and back, and never restarts it for the wait. The report names the tool and when the dialog opened, never the command. A log that can't be read, or a defect in reading it, keeps the last answer and warns by name, since an exception that escaped would end the beat and the core would restart the live session. A denial writes no event of its own, so the session reads as waiting until its next prompt or tool call. An adopted session writes no liveness, so it isn't covered yet. The test R21's row names holds the reading rule and the beat itself, started by the monitor from the session's environment; nine planted defects each fail it.
