### Added

- **`macf_tools ids renumber`: the one-time move of a running deployment onto its declared ids** (`ids/renumber.py`, `ids/renumber_cli.py`, policy `container_operations` 6.2). It runs as root in the old container before the recreate, because only that container's live tables know the old numbers. It maps every framework account and group by name to its declared number, refusing ambiguous or colliding mappings. It re-owns only the framework's volumes and the bind mounts named, never follows a symlink, and stays out of unnamed mounts. The plan comes first, with a listing; bind mounts carry a warning that an old number there may be a host account's, and files with access lists are named. The plan also names files left on a number outside the block that nothing maps (the base image's `ubuntu`, say), which would otherwise pass to the host's holder of that number, and setuid or setgid files that `chown` would clear. After `--apply` it re-plans and fails if anything is left; a second run is a no-op. `--apply` refuses while a process still runs under a user or group number it moves (the amail services, an admin login), and a path that can't be re-owned is named while the rest still move, so a rerun resumes. Start-up now also refuses when `/home/admin` or an amail service directory is owned by another number than its account's slot, naming this step, so a rebuild without it stops instead of leaving the broker unable to read its ledgers. Twenty-six tests (`test_ids_renumber.py`), twelve planted defects each caught. A root run in a throwaway container re-owned all ten old-numbered files, left a symlink's outside target and an unmapped file alone, and found nothing on the second run.
